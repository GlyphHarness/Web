# Contract records on real shapes (B1.2)

Status: hypothesis. Built: nothing; paper check only. 2026-11-21. Records: `docs/platform/contract-records.jsonl` (six lines, one per core contract, PH2). Story: `docs/epics/B1-platform-spine.md` B1.2.
Terms: platform contract, core contract set (catalog); carry check, shape gap (inbox platform-qvbhzt).

## Method
Carry check: for each real shape, name the contract operations that would carry it, field by field; anything left over is a shape gap, written as a hypothesis with its cost, not as a new contract (smallest set first).
Shapes are read from the repo, not invented: source in the first column. The harness is the data source; the platform is not built, so "carried" means "an operation exists whose input or output holds the field", nothing run.
Counts: clean = carried by the six as written; with addition = carried after one field or one operation was added to a record (the addition is already in the records and marked); new contract = needs a seventh.

## Result (paper, this pass)
- Carried by the six: 10 of 10. Clean: 6 (1, 4, 6, 7, 9, 10). With a small addition: 4 (2, 3, 5, 8). New contract: 0. The refutation line (more than three need a new contract) is not reached; concept oivpvb asked for at least 7 of 10 carried: met on paper.
- Additions made to the records because of the shapes (each one already costed in its record): clock.mono, `doc` on every operation, store `prev` (with tie order by sequence in the timestamp rule), identity.issue_id. Four additions across ten shapes is not zero: the set is stable but not untouched.
- One shape worth a seventh contract if the claim is to hold at all: none found. One home that is uncertain: issue_id (an entropy source may deserve its own place; cost one more contract).

## Why this check is weak (stated, not hidden)
- Circular: the six records were written knowing the ten shapes, and four were revised by them. "Carried" is cheap, because every shape here is a keyed value with a time. A shape that a platform author did not see is the real test: B1.6/B1.7 conformance (gated), and B2's shapes (reviewer app, query mapping).
- Surface is unexercised: of the ten shapes only the approval prompt of a concern touches it (and the validator and profile views would be rendered by it). The claim that surface carries anything real has no evidence here. Recorded as unknown, not as carried.
- Time fields are not checked against a running clock; as-of reads over these shapes are B1.4's oracle.
- The harness already holds a precedent: `app/validators.js` `read` normalises a stored session and a profile into one event shape `{session, kind, calls[{turn, msg, call, name, args, cmds}], cost}` through registered readers. It shows two heterogeneous shapes can be read as one event record without a new store, and it is itself unreplayable by time (reads current state).
- Unmerged context (not read as authority): branch `platform-query-notes`, `docs/platform/query-surface.md`, says the query surface is "not a seventh contract" but adds "one generic `ref` contract" (operations property, get, set). If that counts, the set is already seven in effect for query. None of the ten shapes needs it, so it is outside this count; the steward should see the two notes side by side before GB.

## Findings about the harness the check surfaced (not platform design)
- Trail: `TRAIL_MAX = 500`, localStorage slice. History beyond 500 rows is lost; any as-of read over the trail is bounded by it (fault ruksoa).
- Handles: audit is memory only, hash only, cap 2000; re-points overwrite (fault mvoovn).
- Ledger: `kept` and `broke` depend on memory-only `last` (a page reload yields `kept: null`, by design in `measure`).
- Catalog: a day-resolution `since`; only git commit time orders lines within a day.

## Kept
- A seventh contract for randomness, one for blobs (content-hash store, `outstore`) or one for tool definitions: not added. Blobs are a store key policy (content hash as key); tool definitions are module operation records; randomness is identity.issue_id for now. Each would cost a record, bindings and a threat entry.
- Treating the paper count as the claim's result: rejected; see the weakness list.
