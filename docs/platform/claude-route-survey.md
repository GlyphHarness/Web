### Claude Code and Agent SDK facts (documentation read today; the CLI version at read time is not stated by the pages)
- Non-interactive: `claude -p "<prompt>"` (headless page). Output `--output-format text | json | stream-json`; `--input-format text | stream-json`; `--include-partial-messages` needs `-p` and `stream-json`, and the headless page's streaming example also passes `--verbose`; `--replay-user-messages`; `--max-turns`; `--session-id <uuid>`; `--resume <id or .jsonl transcript path>`; `--continue`; `--fork-session`; `--no-session-persistence` (print mode only); `--permission-mode`; `--allowedTools`; `--permission-prompts none`; `--append-system-prompt` and `--system-prompt` (replacing it also drops the git status snapshot). Piped stdin is capped at 10 MB. Exit 0 on success; missing authentication is printed as the result on stdout.
- `--bare` skips hooks, skills, plugins, MCP, auto memory, CLAUDE.md; it "never reads OAuth credentials or the system keychain" and needs `ANTHROPIC_API_KEY` (or an `apiKeyHelper`). It is recommended for scripted and SDK calls and "will become the default for `-p`". So bare mode and subscription login exclude each other.
- `ANTHROPIC_API_KEY`, when set, is used instead of the subscription, and "in non-interactive mode (`-p`) it is always used" (env-vars page, gist). A container with the variable set therefore bills the key, whatever login exists.
- Streaming: partial messages are raw Claude API events (`message_start`, `content_block_start`, `content_block_delta` with `text_delta` or `input_json_delta`, `content_block_stop`, `message_delta`, `message_stop`); a cut stream still ends with `message_stop`, and an open tool call at that point has incomplete input; `message_delta` arrives when the turn is interrupted. Stream events carry the main session only; subagent token deltas are not forwarded. `system/api_retry` events report CLI-side retries (attempt, max_retries, error class). The final `result` message carries cost and session id; `--output-format json` has `total_cost_usd` (a client-side estimate).
- Stopping: SIGTERM exits 143 and records no result for the turn in progress; SIGINT, or the SDK's `interrupt()`, ends the turn; the SDK ends input before signalling. On resume the interrupted turn stays as it is.
- Thinking knobs (gist): `MAX_THINKING_TOKENS` sets a fixed thinking budget when adaptive reasoning is off and `0` disables extended thinking on the Anthropic API; `CLAUDE_CODE_EFFORT_LEVEL` low..max; `CLAUDE_CODE_DISABLE_THINKING` omits the `thinking` parameter (for proxies); `CLAUDE_CODE_MAX_OUTPUT_TOKENS`. Whether a thinking block streams as a `thinking_delta` through the CLI is not stated on the pages read (inferred from the raw API event set; unverified).
- Agent SDK (concrete): a library that "runs the Claude Code binary" (TypeScript `@anthropic-ai/claude-agent-sdk`, Python `claude_agent_sdk`); docs point at API-key authentication; the TypeScript SDK bundles Claude Code from v0.3.290 and the Python SDK from v0.2.164 (streaming page). To drive the loop from another language, "run the CLI as a subprocess" with `-p`.
- Terms (concrete, legal-and-compliance page): OAuth is "intended exclusively for purchasers" of the plans for "ordinary use of Claude Code and other native Anthropic applications". Developers building products or services, including with the Agent SDK, "should use API key authentication"; Anthropic does not permit third-party developers to offer Claude.ai login or to route requests through plan credentials on behalf of their users, and developers "may not collect, store, or intermediate Claude.ai credentials or session tokens". Running Claude Code in a product requires the Commercial Terms, the binary unmodified and no removal of its auth methods; each end user authenticates with their own key or plan credentials; "an end user [may] sign in to the unmodified Claude Code binary with their own Claude subscription", including where a platform hosts it. The SDK overview adds a branding rule: a product must not appear to be Claude Code (the name "Claude Code" is not allowed for the product).

### In-flight gateway facts (documentation read today; concrete unless marked)
- The variable is `ANTHROPIC_BASE_URL` (llm-gateway-connect, llm-gateway). It can be exported in the shell or put in the `env` block of `~/.claude/settings.json`; the settings value wins over a shell export. `/status` shows an "Anthropic base URL" line when it is set. Agent SDK spawns the binary, so it passes the variable through its `env` option (TypeScript: replaces the environment unless `process.env` is spread; Python: merges).
- Wire: Anthropic Messages format. Inference posts to `/v1/messages?beta=true`; `/v1/messages/count_tokens` is optional (without it Claude Code falls back to a character estimate). Streamed responses must be `content-type: text/event-stream`.
- Subscription through a gateway: setting only `ANTHROPIC_BASE_URL` does not replace the subscription; the saved claude.ai login stays the active credential and "its usage limits and billing apply". A gateway that passes such traffic to Anthropic "must forward `Authorization` and the OAuth capability in `anthropic-beta`"; stripping `anthropic-beta` fails those requests with 401. While `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY` (gateway credential) or `apiKeyHelper` is set instead, the saved login is not sent and traffic bills per token to the credential's owner. So both auth modes work behind one base URL, and the gateway is a pass-through for the header in the subscription mode.
- Forwarding rules: forward `anthropic-version` and `anthropic-beta` verbatim; treat headers and body fields as open lists and pass `anthropic-*` headers and body fields unchanged to an Anthropic-format upstream (an allowlisting gateway breaks the next release's feature). Consumable without forwarding: `x-claude-code-session-id` (per session), `x-claude-code-agent-id` and `x-claude-code-parent-agent-id` (subagents). Opt-in hint headers behind a custom base URL, via `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` (v2.1.273 or later): `x-claude-code-request-class` (main, subagent, workflow, compaction, auxiliary), `x-claude-code-compaction`, `x-claude-code-context-compacted` (a cache keyed on the earlier prefix can be dropped), `x-claude-code-prev-tool-durations`, `x-claude-code-prompt-id`. They carry no prompt text.
- Cache-relevant (concrete): the `system` array carries an attribution block first; the first-party endpoint strips it only if the array arrives unchanged and the block stays first and in its own entry; "prepending another system block, reordering the array, or converting it to a single string" lets it reach the model and the cache key. Cache TTL one hour is requested through `ttl` in `cache_control` (plus an `extended-cache-ttl` beta value on the direct path that must be forwarded). When an upstream rejects a `cache_control` marker on a mid-conversation system message, Claude Code retries once with the marker moved to the last non-system message. Hence cache_control normalisation by a gateway is allowed by the pass-through rule only as an option the operator turns on, and it must keep the system array order and its first block.
- Thinking-relevant (concrete): Claude Code requests adaptive reasoning for newer models; on a 400 naming `thinking.type` it retries once with the other type. When an upstream rejects a thinking signature, including "bound to a different conversation", Claude Code removes earlier thinking blocks, retries, and keeps them out of all later requests. So an altered thinking block that returns to the API is a signature risk, with a documented recovery that costs a retry and the cache prefix. `CLAUDE_CODE_DISABLE_ADAPTIVE_THINKING=1` works on Opus 4.6 and Sonnet 4.6 only; the model-capability variables do not apply behind `ANTHROPIC_BASE_URL`.
- Stream-relevant (concrete): response headers to pass: `retry-after` (integer seconds), `x-should-retry`, `anthropic-ratelimit-unified-*`, error bodies unmodified (recovery matches on the upstream's wording). Watchdogs behind a custom base URL: the byte-level watchdog (default 300 s without bytes, keep-alive pings count) and the event-level watchdog (300 s without a parsed event) run; the first-byte deadline does not. A mid-stream abort is a mid-stream failure: Claude Code retries, or keeps the completed output with an incomplete-response notice, or, in a non-interactive session, "may first prompt Claude to continue the cut-off response". A gateway halt must therefore end the stream cleanly (a final `message_delta` with a stop reason and `message_stop`), not by dropping the connection; whether Claude Code accepts a synthetic stop reason without a retry is unverified (R14).
- Telemetry and other traffic: Claude Code also calls hosts outside the gateway path (updates, telemetry, WebFetch safety check, fast-mode check); `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` turns the nonessential part off. They are not model traffic and the gateway need not see them.
- Not read: the rest of llm-gateway-protocol (feature pass-through detail, model discovery format, response-header details past what is cited), llm-gateway-rollout, claude-apps-gateway, prompt-caching page, platform.claude.com extended-thinking and caching pages (in Deferred).

## Design constraint
Intent (operator addendum): wrap the traffic of the real Claude Code in flight, so the harness can place cache_control and keep prefixes stable, bound thinking, and halt or alter the streamed response progressively by budget; once it holds together, Claude is a backend swapped in behind the harness's interop, the same way OpenRouter is today (the harness is a local web app used from a phone; the host is Windows with WSL and podman).

Boundary, two classes of request, kept apart:
1. Requests that originate from Claude Code itself (the real, unmodified binary, installed in the container and signed in by the user inside the container, or given a user-supplied API key as a container environment variable) may pass through the in-flight gateway. The gateway forwards `Authorization`, `x-api-key`, `anthropic-version` and `anthropic-beta` untouched: it never reads, parses, decodes, logs, stores, persists or replays a credential, and it only forwards requests that originate from Claude Code.
2. Requests that originate from the harness (the browser app calling Claude as a provider) never carry or use the subscription login. They use (a) an API key the user supplies as a container environment variable (route C), or (b) the headless / Agent SDK interface of the real Claude Code, which then makes its own requests under class 1 (routes A, B).
The route never extracts, copies, replays or forwards a subscription login token or Claude Code's stored credentials, and no non-Claude-Code client presents itself as Claude Code (no copied `x-claude-code-*` headers, no copied system attribution block, no borrowed `anthropic-beta` OAuth value).

Reason: the subscription login is for Claude Code itself (legal page: OAuth is for ordinary use of Claude Code and native applications by the plan's purchaser; products and services should use API keys; no routing through plan credentials on behalf of users; no collecting, storing or intermediating login credentials or session tokens; the SDK overview forbids a product from appearing to be Claude Code), and CLAUDE.md "Secrets never in files or chat". This is a boundary on what the code may touch, not a suspicion of the user: the user may sign in to their own binary, and the gateway is theirs.

Enforced as checks, with the restrictions as options, off by default (CLAUDE.md):
- Credential blindness: header values are copied by a function that does not inspect them; logs and the harness trace record header names only; a canary value set in the container's environment and in a fake `Authorization` header is searched for in every log, trace, store and exported session (R3, R18).
- Origin: the gateway has two listeners. The Claude Code listener is not published outside the container and only forwards `POST /v1/messages` and `/v1/messages/count_tokens` that carry `x-claude-code-session-id`; anything else gets a 4xx (header presence is a shape check, the isolation is the unpublished listener; R16). The harness listener is the only one published (loopback), and it never forwards a client-supplied credential header: for route C it uses the container's API key variable, if absent it fails closed with a message.
- Docs state the gateway use as normal: `ANTHROPIC_BASE_URL` is the documented way to put a gateway in front of Claude Code, and docs name it for organizations; whether a personal single-user gateway on a subscription login is within terms is not settled by the pages read (Q1). With a user-supplied API key in the container the question does not arise.

## Candidate routes
| | route | how | for | against |
| --- | --- | --- | --- | --- |
| A | Claude Code headless in podman as provider | a shim in the container runs `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages` and answers the page with OpenAI-style SSE | the real unmodified binary serves harness requests; auth stays in the container; combines with E (the headless CLI then talks to the gateway) | the CLI owns the agent loop and its own cache_control placement; stdin message shape and interrupt behaviour unverified |
| B | Agent SDK in podman | a small Node or Python service calls `query()` with `includePartialMessages`, `interrupt()`, hooks, in-process MCP tools | typed events, `interrupt()`, hooks, tools as an MCP server | adds a package and runtime; docs steer products to API keys; same binary underneath; the SDK passes `ANTHROPIC_BASE_URL` through its `env` option so it also combines with E |
| C | API-key provider | harness listener of the gateway receives the page's OpenAI-style request, builds a Messages request, adds the user's API key from the container env, and streams back through the same policy | official, terms-clean, full control of `cache_control`, `thinking`, tools and the stream from the first byte; no CLI in the loop | not the user's Claude Code installation or plan quota; translation between OpenAI-style chunks and Messages events |
| D | mirroring (later) | context kept in sync between the harness and a Claude Code session; one executor per tool call | one conversation, one bill | needs A, B or E first; R9, R10 unproven |
| E | transparent in-flight gateway in the container | the real Claude Code (installed and signed in by the user in the container) runs with `ANTHROPIC_BASE_URL=http://127.0.0.1:<port>`; a gateway there sees request, response and stream bodies, applies policy (cache_control normalisation, thinking parameters, halt-and-alter by budget, a reducer hook), forwards credential headers untouched | documented mechanism (see Kept); works in both auth modes; Claude Code's own session, tools and cache stay intact; the same policy module serves route C | the gateway must forward `anthropic-*` headers and body fields unchanged by default (policy rewrites are opt-in); a halt must end the stream in a form Claude Code accepts without retry (unverified); altering thinking breaks signatures; it serves Claude Code's own turns, not harness-originated ones unless A or B drives the CLI |

How the routes compose: one gateway core (pure policy over Anthropic stream events and request fields) with two ingresses. Ingress 1, E: Claude Code to gateway to upstream. Ingress 2, C: the harness's provider request to gateway to upstream. A and B are the ways a harness request reaches Claude Code (they feed ingress 1 indirectly). D sits on top later.

Pick for step one: E plus C behind one provider seam, text-only for C, one request per turn; A is step two; B and D later. Reasons: (1) the policy the operator wants (cache_control and prefix stability, thinking parameters, halt-and-alter by budget) lives at the wire, and E and C are the two places the wire is reachable without any dependence on CLI flags that I could not verify; (2) C is terms-clean for harness-originated requests and gives the baseline arm (direct vs gateway, R13) and the fully harness-controlled arm (cache_control placement, R15); (3) E is the documented way to wrap the real Claude Code, needs only an environment variable and a listener, and carries both auth modes with no code that handles a credential; (4) the page side is one registry entry: the gateway's harness listener speaks OpenAI-style SSE, so `providers.js` needs no change beyond the entry (R2); (5) A's flags (stdin shape, SIGINT in stream-json mode, a tools-off switch) are unverified, and A gains most only once E exists (the CLI behind A then sees the gateway too). What step one drops: A, B, D, tools in C, mirroring, session reuse, anything that publishes a port beyond loopback.

## Interop / gateway interface (sketch, hypothesis)
Page side: one registry entry, `claude` = `retrying(openaiCompatible({ label: 'Claude (container gateway)', base: 'http://127.0.0.1:<port>/v1' }))`, `needsKey: false` (the key lives in the container), plus a base-URL setting that already exists per provider (R2).

```
page --POST /v1/chat/completions (stream:true, route?:{budget,halt,thinking})--> gateway harness listener (published on loopback)
gateway(C) --POST /v1/messages (system/tools/messages, cache_control by policy, thinking fields by policy; x-api-key from container env)--> api.anthropic.com
claude (real, in container) --POST /v1/messages?beta=true (ANTHROPIC_BASE_URL, own headers)--> gateway Claude Code listener (not published)
gateway(E) --same request, headers verbatim, body by policy (default: unchanged)--> api.anthropic.com
upstream --SSE Messages events--> gateway core --policy per event--> client (page via OpenAI-style chunks, or Claude Code verbatim)
```
- Gateway core, request side: `onRequest(ctx, req) -> req'` pure over body fields; ctx has class (`x-claude-code-request-class` when hint headers are on: main, subagent, compaction, auxiliary), session id, prompt id. Policies, each an option off by default: (1) cache_control normalisation: keep breakpoints on stable prefix positions (tools, system, last stable message), keep the system array order and its first (attribution) block, never reorder; (2) thinking parameters: set or cap the `thinking` budget or `output_config.effort` field on main-class requests; (3) a reducer hook over messages (idea from the stripe reducer: lossy only on the wire, full text behind a handle held by the harness; for E only on the request copy, never on what Claude Code keeps, which it resends itself).
- Response side, the halt-and-alter hook (a pure function, the lexgate / agent-tap shape): `onEvent(state, event) -> { t: 'pass' } | { t: 'halt', reason } | { t: 'alter', event' }`, called at event boundaries only. `state`: counters per block kind (text chars, thinking chars, tool_use input chars), a token estimate (about 4 chars per token), elapsed ms, request class. Budget `{ text, thinking, total }`, each optional, checked after every delta, cheap counter first and a finer lexical check only inside a margin (R8). `halt`: stop reading upstream (aborting the upstream request ends further output billing, to be measured), close open blocks, emit `message_delta` with a stop reason and `usage`, then `message_stop`, in the shape the consumer needs: for Claude Code a complete Messages event sequence (stop reason chosen by test, R14), for the page an OpenAI-style `finish_reason: 'length'` and an `x_halt: { reason, at }` field so it is truncation, not an error. `alter`: rewrites or drops text deltas before forwarding; thinking blocks are not altered or dropped on the E path (signature and tool-loop risk), only on the harness copy of ingress 2 (R7, R17).
- Usage is read from stream events (`message_start` and `message_delta` usage: input, output, cache read, cache creation), which is how cache-hit rate is measured without touching headers (R13).
- Containers: image from the hermes-genesis Containerfile pattern (ubuntu base, non-root user, entrypoint); Claude Code installed by the user's chosen method inside it (install method unverified here); the user signs in once in an interactive session of the container, or passes `ANTHROPIC_API_KEY` by name from their environment into it; the credential store stays in a named volume the gateway process does not mount. The gateway runs as a separate process, with no access to that volume. `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1` in the container. Harness listener on `127.0.0.1` only (Q10); CORS and Private Network Access answers as in `scripts/test-localbridge.mjs` (the local bridge is not used: it buffers).

- R4 Halt at a boundary: a halt ends the stream within one further event, partial blocks are delivered, and the consumer (page, or Claude Code) continues with its next request without error. Falsified if tokens keep arriving, the partial is lost, or the next request fails.
- R5 Progressive budget: a counter check at every delta halts within one delta of the budget and the token estimate stays within 25 percent of the final `usage` output tokens over recorded turns. Falsified if either bound is exceeded.
- R6 Thinking volume without answer degradation: (a) request-side thinking parameters or the container's thinking env lower thinking tokens per turn measurably; (b) a harness-copy reducer over thinking text cuts kept thinking tokens while task outcomes do not fall against the unreduced arm. Falsified if (a) leaves reasoning tokens unchanged or (b) lowers task success.

Falsified if an altered E text delta is not what the next request carries, or if a harness-copy alteration changes Claude Code's own record.
- R8 Terse flow: a terse-style instruction plus a halt budget cuts output tokens per turn by a stated fraction on the same task without lowering completion; the check is a pure lexical function with a trace (no LLM). Falsified if tokens do not fall or completion drops.
- R9 One-way mirror (later): if the harness transcript is the source and the Claude Code session is derived from it (only new messages sent), a hash of the message list stays equal on both sides over N turns and cache reads stay high. Falsified by the first divergent hash or a cache read collapse.
- R10 Mirrored tool calls do not run twice (later): with tool calls seen at the stream by the gateway (E) and one executor chosen per call (harness tools exposed to Claude Code as an MCP server, or the CLI's own tools, never both), every tool call id is executed exactly once; where both targets could run it the host is omitted. Falsified by a call id executed twice or on neither.
- R11 Auth-mode invariance: the gateway behaves the same with a user-supplied API key and with the user's own signed-in binary except that it forwards the same header untouched; the mode is chosen only by the container's environment. Falsified by any code path or output that differs by mode.
- R12 No double retry: the page's `retrying` acts only before the first chunk (at most 2 more tries), Claude Code's own retries stay its own, and the gateway adds none; a turn is never replayed. Falsified if one turn is billed or shown twice, or the gateway's retry plus Claude Code's retry multiplies.
- R13 Cache-hit through the gateway: with E in pass-through mode (no body policy), the cache-hit ratio `cache_read / (cache_read + cache_creation + input)` per turn, over the same scripted session of at least 30 turns, is within 2 percentage points of the direct run. Falsified if it is lower by more than that. The same measure is taken for C against a direct SDK call.
- R14 Halt-and-alter latency and acceptance: the gateway adds under 5 ms per event at p95 (to be set by measurement) and a halt ends the E stream with a synthetic stop sequence that Claude Code accepts without a retry or a "continue" prompt. Falsified if added latency exceeds the bound, or Claude Code retries, continues, or shows an incomplete-response notice for the chosen stop reason.
- R15 cache_control normalisation: with policy on, the cache-hit ratio of a session with churning prefixes (varied tool results, compaction) is not lower than pass-through and is higher in at least one scripted churn case, and the attribution block stays stripped upstream (system array order kept). Falsified if the ratio drops, or a recorded request shows the attribution block reaching the prompt.
- R16 Origin boundary: the Claude Code listener forwards only requests that carry the Claude Code shape and arrive on the unpublished listener; a harness-origin request on the published listener never reaches upstream with a client-supplied credential. Falsified by a forwarded request lacking `x-claude-code-session-id` on the E listener, or any forwarded credential header from the published listener.
- R17 Thinking alteration breaks signatures: dropping or editing a thinking block on the E stream makes the next request be rejected and Claude Code recovers by removing earlier thinking and retrying (a documented recovery that costs the cache prefix), so E must not alter thinking. Falsified if an edited or dropped thinking block is accepted with no retry and no prefix loss.
- R18 Header copy is blind: the pass-through copies header values without reading them: unit check with a function that fails the test if the value is read (a proxy object that throws on access to the value); logs carry names only. Falsified if the check can observe a read, or a value appears in a log.

## Decisions taken at implementation
Core: `app/claude-gateway.js` (one file, 253 lines, no imports; no split was needed). Where the survey was silent:
- Refusal statuses: `admit` answers 404 (route), 405 (method), 403 (Claude Code shape missing, or an `x-claude-code-*` header on the harness listener). The harness listener with no key answers 401 `no-api-key`; not 503, because the page's `retrying` asks again on 502, 503, 504 and 429 and a missing key is not transient (R12).
- `harnessHeaders` also drops the hop-by-hop `host` and `connection`, as `passHeaders` does; `content-length` is the listener's, since a changed body changes it.
- The provider entry's loopback port is 8792 (`providers.claude.base`), a placeholder the listener piece may move; `opt.base` already overrides it. `openaiCompatible` gained a `needsKey` parameter (default true), so the other entries are as they were. With `needsKey` false the page still sends `Authorization: Bearer undefined` as its argument; the harness listener drops client credentials, so nothing reads it.
- cache_control over the limit of four: after the oldest message markers, system markers from element 1 (oldest first) are removed, then the tool marker; `system[0]` is never touched. The spec's reading ("system elements 1.. stay") covers only the case at or under the limit; over it, a request with five or more markers before the messages would be refused by the API, and removal is within "remove or move only". When several tools carry markers, the last such marker moves to the last tool (its own marker wins when it has one).
- Thinking effort order has `xhigh` between `high` and `max`; an effort value not in the order, or a cap not in it, changes nothing. `applied` names `cache.normalise` and `thinking` (one name for budget and effort together).
- Stream: the budget reason codes are `budget-text`, `budget-thinking`, `budget-total` (first reached, in that order); `halt.chars` and the synthetic `usage.output_tokens` use the total characters of the three kinds at the end of the stream. A block of a type other than text (or thinking on the harness listener) is not cut. An altered delta is a new object and a verdict `alter` only when the reducer changed the text; an empty result still sends an empty delta. A reducer returning a non-string leaves the text as it was. An upstream `error` event sets `done` and is passed untouched.
- `sseSplit` also returns `bad`: frames whose data is not JSON, as received, so the listener decides (pass them on raw); nothing is dropped silently.
- Not in the core: the OpenAI-style mapping (reading h), elapsed-time budgets, the lexical margin check (R8), placing markers (route C), OPTIONS and CORS answers of the harness listener.
- `harnessHeaders` forwards an allowlist, not a denylist: `content-type`, `accept`, `anthropic-version`, then its own `x-api-key`. Everything else a client sends (cookie, proxy-authorization, anthropic-beta, transfer-encoding, content-length, origin, any future header) is dropped, so R16 holds for headers not yet invented (fault mkqsxn). The listener sets the headers the upstream call needs that are not client headers (`anthropic-version` when the client sent none, `content-length`). The Claude Code listener stays a blind copy.
- Wrong-shaped input never throws (faults fhkyrn, trbwvd), the listener name excepted (an unknown one is a programming error and throws). `sseSplit` puts frames whose JSON is not an object in `bad`, so `events` hold objects only; `streamStep` passes a non-object on as given. `onRequest` and `normaliseCache` hand back a body that is not a plain object as given (`applied: []`) and skip parts that are not Messages-shaped (a non-array `messages`, a last tool that is not an object keeps all markers where they are). `admit` answers 400 `bad-request` for a request that is not `{method: string, path: string, headers: [[name, value], ...]}`; `passHeaders` and `harnessHeaders` answer 400 `bad-headers` for a header list that is not pairs with a string name (the key check of `harnessHeaders` comes first: 401 `no-api-key`). Only names are read, values stay untouched.
- R4 on the Claude Code listener, a design decision: a halt waits for an open thinking or tool_use block, so the budget is not a bound there. Measured wait: up to 39296 events on a 1 MB thinking stream (`docs/concepts/results/gateway-det-2026-11-21.json`). Reason: cutting thinking breaks its signature (R17) and cutting tool_use breaks the call, and either makes the consumer's next request fail. A budget on this listener is therefore a request to end at the next safe point, and the consumer's own limits stay the only hard cap. On the harness listener thinking is cut at once; tool_use waits on both. A hard cap would end the stream with an error event instead; not built, add it when wanted.
- Slice 1, WSL base (built, environment recipe, no module seam): `scripts/claude-route/setup-wsl.sh` puts a stock Claude Code TUI in tmux session `claude` in WSL distro UbuntuBase (the distro is a parameter). The user signs in there; the setup unsets `ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` for the TUI and never reads or writes auth. `scripts/claude-route/check-wsl.mjs` (red 3d34598, green 8193fe1) passes: distro exists, session exists, `claude --version` 2.1.330. Nothing live is measured: no request has gone through the TUI, so routes C and E stay unmeasured. That a stock sign-in tmux TUI is a sufficient base for the live checks is a hypothesis.
