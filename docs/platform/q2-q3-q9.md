## Coupling
Q2 and Q3 are not independent. `CLAUDE.md` says the harness is "static ES modules in `app/`, no build". An embedder runtime (below) needs a non-JS host and a build, so it cannot live under `app/` or follow the harness release (`main` to GitHub Pages). Q2 = embedder therefore leans Q3 = separate product. Q2 = browser layer leaves Q3 open. Q9 is downstream of both: the baseline has to be one the chosen host's engine ships.

## Q2 scope: embedder runtime or browser layer
README text: "embedder runtime (own host, wasm engine) or layer over a browser (then JS glue exists at the edge)? 'wasm does not bind through JS' differs between them."

| option | what | cost | check that could refute it |
| --- | --- | --- | --- |
| A embedder runtime | own host process embeds a wasm engine and binds every contract natively; surface drawn by the host (candidates from memory, unverified: wasmtime, wasmer, WAMR, wazero) | a non-JS toolchain and build; the surface contract needs a native text, layout, input-method, scroll and accessibility stack; no existing browser features for free | JS values crossing per contract call on the ledger's data path must be 0 (PH1 holds-if); fails if a native text and table surface for the ledger needs more than the threshold below |
| B browser layer | the platform is an app on a browser engine (the harness's own position today); wasm components run on the browser's engine, contracts bound through JS glue at the edge (unverified: a component transpiler such as jco) | every call on the data path crosses JS unless the browser can instantiate components without glue (Q9 survey S9.2); the goal sentence narrows to "wasm does not bind through JS except at the edge" (risk already noted in the epic) | JS crossings per call on the data path greater than 0 is expected; the claim is kept narrow; refuted as an answer to the goal if the goal is read strictly |
| C embedder with a surface adapter | A for clock, stream, store, module, identity; the surface contract bound through a webview or browser adapter (JS only at the surface binding) | two processes and a bridge for surface events (event records over the bridge); the "no JS" claim holds on every contract except surface | JS crossings 0 on the four data-path contracts; adapter must carry surface.events as event records with start and transitions (PH11) without loss |

Measures that settle it, thresholds fixed before any run (hypothesis values; a changed threshold is recorded with its reason):
- M2.1 JS crossings. Count JS values that cross per contract call on the data path while the ledger app reads 1,000 real catalog rows through store.read. A: must be 0. B: counted, expected above 0. C: must be 0 on clock, stream, store, module, identity. Needs a built host: after GB.
- M2.2 Surface need of the first app. List the surface operations the ledger app needs (text runs, table, text input, scroll, clipboard, accessibility tree). Paper, now: the ledger answers questions and runs a digest, so it can start with text and table output and no pointer drawing. Pre-registered: choose C over A if more than 4 distinct surface capabilities must be native for the ledger and M2.1 stays 0 under C; choose A if 4 or fewer.
- M2.3 As-of read cost. Time and memory for the largest real wh dir log under A and under B, same app. Only if both exist; informs, does not decide.
- M2.4 Does a browser run a component with contract imports bound natively and no JS values per call? Doc fact, survey S9.2 below. If yes, B collapses toward A on the data path and Q2 reduces to a surface choice.

Working choice (hypothesis): A for the five data-path contracts, with the surface binding left open between native and adapter (A or C) until B2.4 (look), and a plain text and table surface for B1.
Reason from the project md files: the goal in `docs/platform/README.md` is "not a browser page, not a harness module" and wasm "does not bind through JavaScript"; `.claude/agents/platform.md` starts "from the smallest contract set"; the ledger app needs almost no surface (M2.2), so the expensive part is deferred, not decided.
What flips it: M2.4 yes and a strict goal reading no longer needing A; or M2.2 showing the ledger needs more than 4 native surface capabilities (then C).
Unknown: whether any embedder engine runs the component model with host-native contract implementations as stated (unverified); engine names above are not checked.

## Q3 relation to the harness: separate product or a way to express harness seams
README text: "separate product or a way to express harness seams? Existing 'seam contract' (lilgxn) overlaps in spirit only."

| option | what | cost | check that could refute it |
| --- | --- | --- | --- |
| A separate product | own repo or directory, own toolchain and release; the harness is untouched; shared only through records (catalog, ledgers, logs) read over file and git protocols | the platform's first app needs the harness's records in a readable form without harness changes; two release processes | the ledger app needs a harness code change to read its records (any file touched under `app/` or `scripts/` is a coupling, recorded) |
| B express harness seams | harness seams (`.claude/agents/seams.md`) become contract records and harness modules become components on the platform | a rewrite of working modules; every harness behaviour change becomes a platform change under the strategy rule (a change to what the model sees is a new strategy id); `CLAUDE.md` no-build rule | seam coverage below the threshold: of the 13 seams listed, fewer than 10 expressible as operation records with in, out and errors; the harness CI suites (9: main git cpu keys local validators profile wh vm) break by a platform change |
| C separate product, seams described only | A, plus contract records written for harness seams as documentation and checks, with no runtime binding | records can drift from code; a description is not a seam contract (lilgxn) and must not use that name | described seams disagree with the code at a probe (spot check of three seams against their modules) |

Measures, thresholds fixed first:
- M3.1 Seam expressibility. From `.claude/agents/seams.md` alone (code not read), 13 seams are listed; 9 name operations with signatures (tools, strategies, terminal hooks, handles, checkpoints, shell runner, inventory provider, validate, UI), 1 names only a function (providers `stream()`), 3 name none (policies, machine, coordination). Paper count today: 9 of 13 would need no further reading, 4 need the code read. Pre-registered: B needs at least 10 of 13 expressible after reading the code of the 4; the harness's own seams are not all data-shaped (UI `rule`/`slot` act on DOM nodes, `machine` is an x86 emulator); they are the two least likely to express, which would leave 11 of 13 at best, so the threshold of 10 leaves room for only one more miss.
- M3.2 Coupling test. The ledger app reads a wh dir `log.jsonl`, a profile and the catalog with 0 files changed under `app/` and `scripts/`. Needs a built app: after GB. Any file touched is a recorded concern.
- M3.3 Release coupling. A platform change triggers 0 of the 9 harness CI suites. Paper now, by design under A and C; under B all 9 are exposed.
- M3.4 B1.2's carry check (`docs/platform/real-shapes.md`) is the nearest data: ten real harness shapes carried by the six contracts with 0 new contract, so C costs about one record per seam and no runtime. Weak: circular (see that note).

Working choice (hypothesis): C (separate product, seams described only), with the code in its own place. This is consistent with A under Q2 = embedder.
Reason from the project md files: README says "not a harness module"; `CLAUDE.md` makes the harness static modules with no build and gates releases on its own judge; the epic says release only if the code lives in this repo (Q3 answer), which the embedder cannot satisfy; and the epic's risk list treats "wasm does not bind through JS" as a host claim, not a harness one.
What flips it: M3.1 showing at least 10 of 13 seams expressible and a stated wish to run harness modules on the platform (then B); a decision to keep the platform in this repo with a browser layer (then Q3 is free).
Unknown: where the code lives (a GB input); whether described seams stay in step with code (no check proposed beyond the spot check).

## Q9 wasm feature baseline
README text: "component model, GC, threads: survey later, outside this pass." The baseline fixes what a contract binding may assume of a guest and of the engine.

| option | what | cost | check that could refute it |
| --- | --- | --- | --- |
| A core wasm only | the standardised core features plus an ABI of our own (records laid out in linear memory, ptr and length), generated from contract records | a binding generator per guest language; no shared tooling; every contract call is ours to marshal | clock bound twice (native and wasm) from one record gives different results, or a guest language has no way to call it |
| B component model | contract records generate (or are compiled to) the component interface types of the component model (WIT text and canonical ABI, unverified naming); catalog term "wasm component" (ksycxw) already assumes it | depends on the standard's and the engines' maturity (unverified: async and stream types were still being finalised); WIT as an IDL is text, and the records carry more than it does (time fields, error names, protocol ids, delegation scope) | survey S9.1 or S9.2 shows fewer than two independent engines ship what the contracts need; the generated WIT cannot hold a time field and the record stays the only source |
| C component model plus GC, exceptions and tail calls | B and the later core features (unverified: finalised as a wasm 3.0 line in 2025) for guests in garbage-collected languages | a bigger engine requirement; fewer embedders qualify; GC guests escape the linear-memory model of contracts | fewer than two independent non-browser engines ship them; no named guest needs them |

Measures, thresholds fixed first:
- M9.1 Feature matrix (survey): for each of component model, GC, exceptions, tail calls, threads, SIMD, memory64, multiple memories, async and stream types: proposal phase, independent engines shipping, source and date. Pre-registered rule: a feature enters the baseline if at least 2 independent embedders ship it (and, if Q2 is a browser layer, 2 browser engines) and a contract binding needs it. Threads stay out regardless (PH2 not-in-the-six: module plus stream instead).
- M9.2 Bind probe (after GB): the clock record bound natively and as a wasm component in two engines, equal results on a shared input list (PH1 holds-if), with 0 JS values crossing on the embedder path.
- M9.3 Guest reach (survey): at least 2 guest languages emit a component for the chosen baseline from a stable toolchain, otherwise the platform is one language, not a platform.
- M9.4 Record richer than WIT (paper, doable now): take the six contract records and list what a WIT view could not hold. Candidates by inspection: `time` field lists, `errors` names beyond a variant, `emits`, binding kinds. If WIT cannot hold them, the record is the source and WIT a lossy generated view, which is how option B is stated below.

Working choice (hypothesis): B, with the contract record as the only source and WIT, if used, a generated view; threads and GC out of the baseline until M9.1 says otherwise.
Reason from the project md files: the catalog already names the unit "wasm component" (ksycxw) and `contracts.md` PH1 holds-if requires one record to be bound by two implementations; PH2 leaves threads out; `contracts.md` Kept rejects "contract as an IDL in prose" and requires data, which is the reason the record, not WIT, is the source.
What flips it: M9.1 showing the component model shipped in fewer than 2 independent engines (then A); a named guest that needs GC (then C).
Unknown: everything in M9.1 and M9.3; I did not search. The component model, WASI versions and the 2025 wasm release status above are from memory only (unverified).
