## Questions (14: 5 lookup, 5 aggregation, 4 locate-then-act)
Every question carries the same preamble (the supersedes rule, "use the folder tools, do not guess", final line `ANSWER: <value>`); the exact prompt is in the jsonl `prompt` field. Expected values are computed by `expect()` in the script from the snapshot (current view = records nothing supersedes; chain tail by following `supersedes`; sums and counts over `rows`), never by a model.

Limit, stated plainly: shape (c) is locate-then-act, but stage 0 has no write tool for the folder (local bridge tools are read-only). The act is stated (which id, which line), not applied. A write-and-diff variant is not tested. The questions are lookups of a kind a model could also answer by fetching less than the whole file; the corpus does not claim to prefer one reading strategy.
Overlap: q05 and q10 use the same file, q02 and q04 the same catalog, by design (the same read, different asks).

## Scoring (fixed before any run)
Answer = the last line `ANSWER: <value>` of the model's final reply. Normalize both sides: lowercase, drop backticks and quotes, drop trailing punctuation, collapse spaces. Solved = exact match. No partial credit, no model judge. Tokens per solved task (jwpfzs) = ledger prompt+completion over the session's requests, divided by 1 for a solved task, undefined for an unsolved one; cost from the ledger. Spread reported as min, median, max over the runs; never one run.

### Protocol addition: continuation nudge (2026-11-21, own commit, reason below)
Not part of the scoring rule above, added to the run protocol afterwards. The harness stops a run after 8 tool rounds (`stops.why = limit`). Rule: when a message ends on a `limit` stop, the driver sends one fixed word, "Continue.", and waits again, at most 3 times per session; the count is recorded per row (`nudges`) and scoring is unchanged (last ANSWER line, exact match, none = not solved). Reason: the first smoke (4 sessions, no nudging, output not kept in the repo) had both models end on the limit with no answer, so a solve rate without it would measure the round limit, not the data path. What is evidenced: the committed smoke file shows nudging already on (nudges 3, 2, 3, 3); canary and full rows all carry the count. "Added before any scored row" rests on the author's statement and the commit order (the rule lives in scripts/a1-baseline.mjs, first committed in c25f096 together with the first canary rows); no earlier commit records it. Results are reported both ways (nudged and first-message) in a1-baseline-2026-11-21.md.

## The arms' view of the data (per arm, PROGRAMME Isolation)
Each arm gets its own copy of the snapshot, same pinned bytes (hashes above), no expected answers, no corpus jsonl, no repo checkout.
- **Stage-0 baseline (arm `stem-1.0`, run in A1.1).** Strategy `strat-stem-1.0` on the main build (v0.56.0, `app/` equal to main). Data path: local bridge (`localbridge/wh-local.mjs --dir data=<own copy>`), tools local_info and local_read (read-only), plus the harness tools of stem-1.0. Its own wh dir, daemon port, bridge port and salt; the page served from this worktree. The corpus, expected answers and this repo are not mounted; the bridge lists only `data`. The model cannot see another arm's copy because there is none running.
- **Arm `serial-2.0` (A1.5, not run).** Same copy of the data via the same bridge and tools, ranged reads (`strat-serial-2.0`). View: identical bytes; differs in how reads are cut.
- **Arm `query-1.0` (A1.5, not built).** The same bytes, through the query surface (result-set header, kinds, labels, query_ref). Its view is not defined yet; it is fixed in A1.3 and recorded here when it is. Nothing is claimed about it.
- Every arm records: working copy path, token's repository list (none: the bridge reads a folder; the OpenRouter key is not a repository token), salt, and whether another arm's copy existed while it ran.
