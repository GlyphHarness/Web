# A1.1 stage-0 baseline: read-path corpus under strat-stem-1.0 (2026-11-21)

Story A1.1 of epic A1 (docs/epics/A1-read-path.md). Corpus, expected answers, scoring rule and per-arm view: `a1-corpus-2026-11-21.md` (+ `.jsonl`). Concept record: `beiyod` (inbox `catalog/inbox/context-hxdvpy.jsonl`). Descriptive: turn metadata only (sizes, counts, costs, stops), no verdict on a strategy.

## What ran

- Arm: `strat-stem-1.0`, the main build (v0.56.0), page served from this worktree; data behind the local bridge, read-only folder `data` (tools local_info, local_read; the harness also gives run_js, output_read, scratchpad and the stem tools). No repository token, no other arm running, no corpus or expected answers in the folder.
- Models (cheap, non-Anthropic only): `tencent/hy4-flash`, `qwen/qwen3.7-flash`, via OpenRouter. Key read from the secrets file in process, never written; each session had its own browser context (no profile on disk).
- Corpus: 14 questions (5 lookup, 5 aggregation, 4 locate-then-act), pinned data snapshot (hashes in the corpus file). Scoring: last `ANSWER:` line, normalized exact match, no partial credit; no ANSWER line = not solved.
- Runs: 3 per model per question: 14 questions x 2 models x 3 runs = 84 sessions. Run 1 tagged `canary` (cap 1.00), runs 2 and 3 tagged `full` (cap 3.00). Every session: new session, its own random salt in the system field, local tools switched on, one prompt. Order of the two models alternates per question and run.
- Nudge rule (operator, fixed word, counted): the harness stops a run after 8 tool rounds (`stops.why=limit`). When the last stop is `limit`, the driver sends "Continue." and waits again, at most 3 times. Chronology as far as it is evidenced: a first smoke without nudging (4 sessions, output not kept) ended on the limit with no answer for both models; the nudge loop was then added and the smoke repeated, and the committed smoke file is that second smoke, already with nudging (nudges 3, 2, 3, 3). The canary came after. "Before any scored row" rests on the author's statement and the commit order (the rule is in `scripts/a1-baseline.mjs`, first committed in c25f096 with the first canary rows); the rule was written into the corpus protocol afterwards, in f25292b. The nudges count is in each row.
- Cost of the whole baseline: $0.162 for the 84 scored sessions (qwen $0.097, hy4 $0.065); plus $0.015 smoke and $0.003 on the discarded cut rows (below), about $0.18 in all (not counting two small debug sessions outside the files). No Anthropic model, nothing expensive.

## Result

Solved over 3 runs, nudged protocol (up to 3 "Continue." per session; first-message numbers below; rows in `a1-baseline-2026-11-21.jsonl`):

| model | all | lookup (15) | aggregation (15) | locate-then-act (12) | per-run solved of 14 (r1 r2 r3) |
|---|---|---|---|---|---|
| qwen/qwen3.7-flash | 27/42 = 64% | 15 = 100% | 6 = 40% | 6 = 50% | 9, 10, 8 |
| tencent/hy4-flash | 34/42 = 81% | 15 = 100% | 8 = 53% | 11 = 92% | 12, 11, 11 |

Spread over the 3 runs (per-run solve rate, min / median / max): qwen 57 / 64 / 71, hy4 79 / 79 / 86. Per question: q01-q05 and q07 solved 3/3 by both; q06 0/3 by both; q08 1/3 by both; q09 hy4 3/3, qwen 0/3; q10 qwen 2/3, hy4 1/3; q11 hy4 3/3, qwen 0/3; q12 3/3 by both; q13 hy4 3/3, qwen 1/3; q14 2/3 by both.

Threshold of `beiyod` (at least half per model; refuted if both under 30%): met under the nudged protocol by both models (64%, 81%).

Negative / caveat, stated plainly: the single-message solve rate (no "Continue." needed) is far lower: qwen 12/42 = 29%, hy4 7/42 = 17%. Of the solved sessions, qwen 1 and hy4 3 needed all three nudges. On that single-message reading both models would sit under 30%, the refutation line. The baseline therefore holds only with the continuation nudges; the 8-round limit, not wrong answers, is the dominant way the stage-0 arm fails.

How the 23 unsolved of 84 failed: 19 sessions ended on the limit stop after 3 nudges with no ANSWER line (5 sessions in all carried a "Branch token budget reached" notice); 4 gave a wrong answer (qwen: q10 142 vs 122, q09 8459688 vs 2819896, q11 pyznac vs uddhvk, q13 "qysjih 32" vs "wqzfte 76", i.e. a stale chain element or a wrong aggregate); hy4 produced no wrong answer, only limit stops. Aggregation sessions fail by running out of rounds (14 of the 16 aggregation failures are limit stops), q06 never solved by either model in 6 tries.

## Turn-analysis notes (descriptive)

- Tool mix (all 84 sessions): output_read is 454 of qwen's 693 calls and 633 of hy4's 834: the model reads large files through the output store in 18,002-character pages (the first local_read result lands in the store, TENET 25) and pages through it, rather than computing. run_js is 121 (qwen) and 68 (hy4) calls; the models try to count in code after reading.
- Median 15 (qwen) and 13.5 (hy4) model requests per session, median 60 s and 48 s, max 221 s and 289 s. Nudge distribution (0/1/2/3 nudges): qwen 12/11/6/13, hy4 7/16/8/11.
- Lookups with a known id cost the least and are solved always. The expensive path is any question that needs a full pass over a file (counts over the current view, sums over ledger rows) through 18k-character pages.
- hy4 uses more tokens per solved task (it reads more, 92% cached) but costs less per solved task in dollars, with failures counted ($0.00192 vs $0.00358); qwen uses fewer tokens per solved session and fails more on aggregation and the longest chains.
- Cached share of the prompt per session ranges 29% to 94% (aggregate share per model above); not analysed further.

## Protocol notes and discarded rows

- Canary rows q01 to q08 (both models) and q09 (qwen) were collected in one persistent browser profile; q09 (hy4) onward and all `full` rows in a fresh context per session. The change was made after a stalled session on a reused profile (the same session id came back after a restart, 0 requests recorded). Fresh contexts removed it; no other change to prompts, rule or scoring.
- Driver faults kept apart, not scored: `a1-baseline-cut-2026-11-21.jsonl` (3 rows: one q08 hy4 per-session timeout from a cut long session, one race row with 0 ledger rows, one q09 hy4 stalled session) and `a1-baseline-smoke-2026-11-21.jsonl` (4 smoke sessions run with nudging on: qwen q01 and both models q06 ended on the limit after 3 nudges with no answer, hy4 q01 solved after 2; not scored). q09 hy4 was rerun in a fresh context as part of the canary.
- Driver and report: `scripts/a1-baseline.mjs` (own driver because `wh.mjs` has no per-session local-tools switch), `scripts/a1-report.mjs` (aggregates the jsonl). Plain-node suites `test-validators` and `test-profile` pass in this worktree; the browser smoke suites and `test-wh.mjs` were not run (G0 not run for the browser seams; no app code changed).
- Version: the baseline arm is the v0.56.0 build; dev is now 0.57.0. Re-measure the stage-0 arm on the current build before any A1.5 comparison; this baseline is not a drop-in reference for a later build.
- Not tested: serial-2.0 and query-1.0 arms (A1.5, not built); a second corpus; other cheap models; the nudge rule's effect on cost (nudge count is recorded, not varied); whether a different round limit changes the aggregation result.
